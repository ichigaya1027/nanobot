# NapCat 多群共享上下文方案

## 1. 目标与范围

同一 Nanobot 实例、同一 NapCat 渠道中接入 GAF 的群共用一条 Agent 上下文。模型可以结合所有接入群的消息思考，并通过工具明确选择向哪个接入群发送文字、语音或执行其他 QQ 动作。

已确认采用完整的共同上下文，而非仅共享长期记忆或通过工具查阅其他会话；模型可以向任意接入群采取动作。本文暂按私聊不并入共同聊天上下文规划，私聊范围尚待确认。不同实例之间的会话同步不在本次范围内。

## 2. 现有实现

- [GroupObserver](../../nanobot/channels/napcat/group_agent.py) 按群攒批，发布时固定使用 `napcat:group:<group_id>` 作为会话键；现有 `unified_session` 不会覆盖这个显式键。
- [GroupRun](../../nanobot/channels/napcat/group_tools.py) 每轮绑定一个群，工具观察到其他群的消息时会报错，动作和历史查询也使用这个绑定群。因此不能只把多个批次改成同一个会话键。
- [ContextBuilder](../../nanobot/agent/context.py) 在同一 workspace 内读取相同的 `SOUL.md`、`USER.md` 和 `memory/MEMORY.md`，长期记忆已有共享基础。共享文件不等于共享各群的聊天记录和压缩摘要。
- [原生会话查询](../../nanobot/session/history.py) 读取可见 user/assistant 正文，不能完整呈现 GAF 通过工具发送的 QQ 消息。它可以查询 Agent 会话，但不替代 NapCat 原始群历史查询。

## 3. 配置与会话归属

在现有 `channels.napcat.groupAgent` 下增加 `sharedContext`，默认 `false`。开启时，现有 `groupAgent.groups` 中通过 `allowGroups` 授权的群全部加入共同上下文，不另外建立一套群名单或多套共享分组。

```json
{
  "channels": {
    "napcat": {
      "groupAgent": {
        "enabled": true,
        "groups": ["123456789", "987654321"],
        "sharedContext": true,
        "batchSeconds": 120,
        "directedBatchSeconds": 10
      }
    }
  }
}
```

共享会话使用独立于具体群地址的固定会话键，例如 `<channel>:gaf:shared`；真实群地址继续保留为 `group:<group_id>`。会话键决定上下文、锁和任务队列，真实群地址决定消息来源或动作去向，不再从共享会话键反推目标群。

同一共享会话复用现有 Session、worker、steer、checkpoint、恢复和上下文压缩机制。普通消息仍按群等待 120 秒，直接 @、回复机器人及戳机器人仍按群等待 10 秒，均沿用可配置的现有窗口。不同群的批次成熟后进入同一会话队列；不另建模型循环或跨群同步服务。

## 4. 消息表示与运行状态

每个批次继续保留 `QQ group <group_id> <group_name>` 头部、北京时间、QQ 号、消息 ID、引用和附件。相邻群批次也保留各自头部，不让发送者或时间的省略状态跨块继承。运行上下文提供接入群的群号和名称，供模型选择工具目标。

把当前单群 GroupRun 改为能够观察接入群的运行状态。消息、发送回执与可操作目标按 `(group_id, message_id)` 关联；昵称按群解释，同一个人的跨群身份以 QQ 号关联。收到其他接入群的 steer 批次时，将其加入同一运行的已观察目标。

沿用现有消息时序投影，并扩展到共享会话中的跨群动作：若 B 群消息在 A 群动作回执之前已经到达，即使 B 群批次稍后才成熟，也能在模型请求中放回对应工具调用与回执之间。原始会话仍按运行时顺序追加，不通过简单排序拆散已保存的工具调用链。

## 5. QQ 工具的目标

共享模式下，所有面向具体群的 QQ 动作和原始消息查询都显式接收 `group_id`。群号直接决定目标，不使用“最后收到消息的群”作为隐藏默认值。`stay_silent` 结束本次共同回应，不需要群目标。

例如模型在一轮响应中可以同时返回：

```json
[
  {
    "name": "reply_message",
    "arguments": {
      "group_id": "123456789",
      "message_id": "#123",
      "content": "收到，我看看",
      "end_response": false
    }
  },
  {
    "name": "send_voice",
    "arguments": {
      "group_id": "987654321",
      "text": "派蒙来啦！",
      "end_response": true
    }
  }
]
```

工具沿用既有群授权与 GAF 接入范围，结果明确返回实际群号和消息 ID。引用和表情等操作按目标群查找消息；当前已支持的引用 ID 可带或不带 `#` 前缀。通用 message 工具向这些 QQ 群发送时，也进入相同的目标选择与发送路径。

同一模型响应中，只有全部工具调用成功，且至少一个调用设置 `end_response=true`，才跳过下一次模型请求。部分失败时返回整组结果，保持已有成功动作的事实。

## 6. 长期记忆、摘要与历史查询

长期记忆继续使用当前 workspace 的文件，不为每个群创建副本，也不增加双向同步。共享会话使用一份压缩摘要；摘要中的群内约定、成员偏好、任务和事件必须保留来源群号、相关 QQ 号和必要时间，避免把某群的事实当成所有群的共同事实。

原始群聊天记录仍通过 NapCat 获取。跨群查询通过工具显式选择 `group_id`，使用相同的行式渲染和历史覆盖说明；不把 Agent 会话数据库当作完整 QQ 历史库。

本功能不以开启 Dream 为前提，实施时不编辑人格内容。当前 Dream 的启停状态独立于共享开关；如果沿用自动整理，需要让传给整理模型的材料保留群来源。现有 `history.jsonl` 可记录 `session_key`，但共享会话键本身不能区分来源群，摘要也必须保留这层信息。

私聊不并入共同聊天上下文，并不意味着长期记忆文件自动隔离：同一 workspace 当前本就共享这些文件。如果要求私聊记忆也不能流入群聊，应作为单独的明确需求处理。

## 7. 定时任务、回流与会话控制

定时任务的执行上下文指向共同会话，任务仍保存明确的所属群。共享模式下创建 QQ 群定时任务时必须确定 `group_id`，不能沿用最先触发本轮的群作为默认目标。通过渠道适配复用现有 cron 服务与任务存储，不新增调度器。

子任务返回、恢复中的输入和其他回流也进入同一会话队列，保留来源信息。统一会话归属的规则由 NapCat 提供，接入现有 gateway 投递流程；核心执行层不硬编码 QQ 群号。

`/new` 和 `/stop` 按会话工作，因此在共享模式下影响全部接入群：`/new` 开始新的共同聊天上下文，`/stop` 停止共同运行。长期记忆不会因 `/new` 被删除。管理界面应说明这种作用范围。

## 8. 切换与已有数据

开启前等待现有批次提交、正在执行的模型和工具动作完成，再按现有配置应用方式切换，避免旧群 worker 与共同 worker 同时处理消息。

创建新的共同会话，保留各群原有会话供查看。建议复用现有压缩能力，首次切换时为各群现有上下文生成带来源的摘要，合并为共同会话的初始背景，随后由新消息延续。摘要会省略细节，需要原文时继续查询 NapCat。不把旧的多套工具调用链直接拼接或按时间重新排序。

已有群定时任务需要检查并迁移会话归属，保留原群目标。关闭共享模式时恢复逐群接收新消息，不尝试把已有共同上下文自动拆回多个群。

## 9. 实施步骤与验收行为

实施分为四步：

1. 明确私聊范围和首次导入摘要的群范围；记录下列验收行为。需要修订测试时先按确认的行为单独处理，再修改实现。
2. 增加配置及管理界面说明，接通统一会话归属和多群 steer。
3. 改造 QQ 工具的显式群目标与按群目标状态，接通定时任务及回流，并保留摘要来源。
4. 根据已有会话和定时任务清单执行切换，验收后再部署。

验收至少覆盖：

- A、B 群消息进入同一会话；A 群提到的内容在后续 B 群请求中可见。
- A 群模型请求进行中，B 群成熟批次可以通过 steer 进入，来源和顺序正确。
- 模型一轮可向 A 群发文字、向 B 群发语音，每个回执都对应实际目标；部分失败时不会把整组当作成功结束。
- 目标群与引用消息匹配，昵称不同但 QQ 号相同的人能够正确关联，图片和引用保留来源。
- 压缩、重启和恢复后仍使用共同上下文，关键事实的群来源保留。
- 定时任务进入共同会话，并发往明确的所属群；`/new`、`/stop` 的实际作用范围与界面说明一致。
- 关闭开关时，逐群会话模式仍按现有规则工作。

共同上下文会更快增长，并使各群共用一个模型执行序列；一个较慢的请求可能推迟其他群的回应。缓存能复用稳定的共同前缀，但总费用也受合并后的历史长度和压缩频率影响，不能预先承诺比独立群会话便宜。
