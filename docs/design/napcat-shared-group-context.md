# NapCat 群聊与私聊共享上下文方案

## 1. 目标与范围

同一 Nanobot 实例、同一 NapCat 渠道中，接入 GAF 的群和所有通过现有授权的 QQ 私聊共用一条 Agent 上下文。模型可以结合这些聊天的消息思考，并通过工具明确选择向哪个接入群或私聊发送文字、语音或执行相应 QQ 动作。

已确认采用完整的共同上下文，并将所有通过现有授权的 QQ 私聊并入。模型可以在群消息触发的一轮中主动选择私聊目标，也可以在私聊触发的一轮中选择接入群。私聊内容因此会出现在群聊推理所用的上下文中，模型可能在群回复中引用这些内容。不同实例、不同 NapCat 渠道及其他平台的会话不在本次合并范围内。

## 2. 现有实现

- [GroupObserver](../../nanobot/channels/napcat/group_agent.py) 按群攒批，发布时固定使用 `napcat:group:<group_id>` 作为会话键；现有 `unified_session` 不会覆盖这个显式键。
- [GroupRun](../../nanobot/channels/napcat/group_tools.py) 每轮绑定一个群，工具观察到其他群的消息时会报错，动作和历史查询也使用这个绑定群。因此不能只把多个批次改成同一个会话键。
- [NapCat 私聊入口](../../nanobot/channels/napcat/runtime.py) 当前直接提交正文和附件，使用普通 Agent 回应及最终正文投递。共享模式需要统一群聊与私聊的消息表示和回应策略，避免整轮行为取决于最先触发的聊天类型。
- [ContextBuilder](../../nanobot/agent/context.py) 在同一 workspace 内读取相同的 `SOUL.md`、`USER.md` 和 `memory/MEMORY.md`，长期记忆已有共享基础。共享文件不等于共享各群的聊天记录和压缩摘要。
- [原生会话查询](../../nanobot/session/history.py) 读取可见 user/assistant 正文，不能完整呈现 GAF 通过工具发送的 QQ 消息。它可以查询 Agent 会话，但不替代 NapCat 原始群历史查询。

## 3. 配置与会话归属

建议在 `channels.napcat` 下增加 `sharedContext`，默认 `false`。开启时，现有 `groupAgent.groups` 中通过 `allowGroups` 授权的群，以及通过现有私聊授权的输入，全部加入共同上下文。群聊继续按群授权，私聊继续按用户及现有配对授权；复用这些范围，不另外建立共享名单或多套共享分组。

```json
{
  "channels": {
    "napcat": {
      "sharedContext": true,
      "groupAgent": {
        "enabled": true,
        "groups": ["123456789", "987654321"],
        "batchSeconds": 120,
        "directedBatchSeconds": 10
      }
    }
  }
}
```

共享会话使用独立于聊天地址的固定会话键，例如 `<channel>:shared`；真实聊天地址继续使用 `group:<group_id>` 或 `private:<user_id>`。会话键决定上下文、锁和任务队列，聊天地址决定消息来源或动作去向。群批次和私聊入口都显式指定共享会话键，使其不受全局 `unified_session` 路由覆盖；WebUI 和其他渠道继续使用各自现有路由。

同一共享会话复用现有 Session、worker、steer、checkpoint、恢复和上下文压缩机制。群消息沿用各自现有的可配置攒批窗口，默认普通消息 120 秒、定向消息 10 秒。建议私聊沿用当前立即提交的节奏。成熟群批次和私聊输入进入同一会话队列，运行中的后续输入使用 steer。

## 4. 消息表示与运行状态

群批次保留 `QQ group <group_id> <group_name>` 头部，私聊输入使用 `QQ private <user_id> <nickname>` 头部，两者共用北京时间、QQ 号、消息 ID、引用和附件的行式表示。每块消息独立保留来源，不让发送者或时间的省略状态跨块继承。运行上下文提供接入聊天的 `chat_id`、类型和名称，供模型选择工具目标。

把当前单群 GroupRun 改为能够观察接入群和私聊的运行状态。消息记录使用 `chat_id` 表示来源，群背景作为群消息的信息附带。消息、发送回执与可操作目标按 `(chat_id, message_id)` 关联；昵称按来源解释，同一个人在不同群和私聊中的身份以 QQ 号关联。收到其他聊天的 steer 输入时，将其加入同一运行的已观察目标。

沿用现有消息时序投影，并扩展到共享会话中的跨聊天动作：若私聊或 B 群消息在 A 群动作回执之前已经到达，即使群批次稍后才成熟，也能在模型请求中放回对应工具调用与回执之间。原始会话仍按运行时顺序追加，不通过简单排序拆散已保存的工具调用链。

## 5. QQ 工具的目标

共享模式下，面向具体聊天的 QQ 动作和原始消息查询都显式接收现有地址格式的 `chat_id`，例如 `group:123456789` 或 `private:10001`。需要在群里指定成员的动作继续接收 `user_id`。工具目标不随首条输入或最后一条 steer 消息隐式变化。`stay_silent` 结束本次共同回应，不需要聊天目标。

建议共享会话始终采用现有 GAF 的工具回应策略，群聊和私聊的文字、语音都通过明确目标的工具发送。最终 assistant 正文不自动投递到触发聊天；这使私聊触发、群聊触发及混合 steer 使用同一套回应方式。

例如模型在一轮响应中可以同时返回：

```json
[
  {
    "name": "reply_message",
    "arguments": {
      "chat_id": "group:123456789",
      "message_id": "#123",
      "content": "收到，我看看",
      "end_response": false
    }
  },
  {
    "name": "send_voice",
    "arguments": {
      "chat_id": "private:10001",
      "text": "派蒙来啦！",
      "end_response": true
    }
  }
]
```

工具目标使用已接入的群聊和私聊，结果明确返回实际 `chat_id` 和消息 ID。引用和表情等操作按目标聊天查找消息；当前已支持的引用 ID 可带或不带 `#` 前缀。群 @ 等群专属参数仅用于群目标，私聊支持的发送、历史及戳一戳动作使用对应 NapCat 接口。通用 message 工具向这些 QQ 聊天发送时，也进入相同的目标选择与发送路径。

同一模型响应中，只有全部工具调用成功，且至少一个调用设置 `end_response=true`，才跳过下一次模型请求。部分失败时返回整组结果，保持已有成功动作的事实。

## 6. 长期记忆、摘要与历史查询

长期记忆继续使用当前 workspace 的文件。共享会话使用一份压缩摘要；摘要中的群内约定、私聊要求、成员偏好、任务和事件必须保留来源 `chat_id`、相关 QQ 号和必要时间，避免把某次私聊要求或某群的约定当成所有聊天的共同事实。

原始聊天记录仍通过 NapCat 获取。工具显式接收 `chat_id`，按聊天类型选择群历史或私聊历史，使用相同的行式渲染和历史覆盖说明。NapCat 官方列出了 `get_friend_msg_history`、`friend_poke` 和群聊对应动作，见 [API 接口文档](https://napneko.github.io/onebot/api)。Agent 会话用于保存推理上下文，不充当完整 QQ 历史库。

本功能不以开启 Dream 为前提，实施时不编辑人格内容。当前 Dream 的启停状态独立于共享开关；如果沿用自动整理，需要让传给整理模型的材料保留聊天来源。现有 `history.jsonl` 可记录 `session_key`，但共享会话键本身不能区分群聊和私聊，摘要也必须保留这层信息。

## 7. 定时任务、回流与会话控制

定时任务的执行上下文指向共同会话，任务仍保存明确的目标 `chat_id`。共享模式下创建 QQ 定时任务时必须确定群聊或私聊目标；任务触发时即使正在处理其他聊天，目标也保持不变。通过渠道适配复用现有 cron 服务与任务存储，不新增调度器。

子任务返回、恢复中的输入和其他回流也进入同一会话队列，保留来源信息。统一会话归属的规则由 NapCat 提供，接入现有 gateway 投递流程；核心执行层不硬编码 QQ 群号或私聊用户。

`/new` 和 `/stop` 按会话工作，因此在共享模式下影响全部接入群和私聊：`/new` 开始新的共同聊天上下文，`/stop` 停止共同运行。命令准入继续使用既有规则，长期记忆不会因 `/new` 被删除。管理界面应说明这种作用范围。

## 8. 切换与已有数据

开启前等待现有群批次提交、正在执行的模型和工具动作完成，再按渠道配置实际需要的重启方式切换，避免旧会话 worker 与共同 worker 同时处理消息。

创建新的共同会话，保留各群及私聊原有会话供查看。已确认首次开启时复用现有压缩能力，为此次接入的各旧会话生成带来源的摘要，合并为共同会话的初始背景，随后由新消息延续。每份摘要保留 `chat_id`、相关 QQ 号、必要时间、未完成事项及其目标聊天。摘要会省略细节，需要原文时继续查询 NapCat。已有全局统一会话可能混有 WebUI 或其他渠道消息，迁移时仅纳入本次接入范围内、具有明确 QQ 来源的内容；不把整段跨平台历史自动并入。旧的多套工具调用链保留在原会话中。

已有 QQ 群聊和私聊定时任务需要检查并迁移会话归属，保留原聊天目标。关闭共享模式时恢复原有群聊和私聊路由，不尝试把共同上下文自动拆回多个聊天。

## 9. 实施步骤与验收行为

实施分为四步：

1. 根据已确认的接入范围、动作目标和摘要迁移方式，收敛其余实施细节并记录下列验收行为。需要修订测试时先按确认的行为单独处理，再修改实现。
2. 增加配置及管理界面说明，统一群聊和私聊输入，接通共同会话归属及跨聊天 steer。
3. 改造 QQ 工具的显式聊天目标和回应策略，接通定时任务及回流，并保留摘要来源。
4. 根据已有会话和定时任务清单执行切换，验收后再部署。

验收至少覆盖：

- A、B 群及已授权私聊进入同一会话；其中一个聊天提到的内容在后续其他聊天的请求中可见，未授权消息按原规则拒绝。
- 群请求进行中，私聊输入和其他群成熟批次可以通过 steer 进入；私聊请求进行中也能接收群批次，来源和顺序正确。
- 模型一轮可向 A 群发文字、向私聊发语音，每个回执都对应实际目标；部分失败时不会把整组当作成功结束。
- 目标聊天与引用消息匹配，昵称不同但 QQ 号相同的人能够正确关联，图片和引用保留来源。
- 群聊、私聊及混合输入使用相同的工具回应策略，最终正文不会被重复投递或隐式发给错误聊天。
- 压缩、重启和恢复后仍使用共同上下文，关键事实的聊天来源保留。
- 定时任务进入共同会话，并发往明确的群聊或私聊；`/new`、`/stop` 的实际作用范围与界面说明一致。
- 关闭开关时，群聊和私聊恢复现有路由，WebUI 和其他渠道不受这个开关影响。

共同上下文会更快增长，并使接入群和私聊共用一个模型执行序列；一个较慢的请求可能推迟其他聊天的回应。缓存能复用稳定的共同前缀，但总费用也受合并后的历史长度和压缩频率影响，不能预先承诺比独立会话便宜。
